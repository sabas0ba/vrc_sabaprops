# 設計

このパッケージがなぜこの形をしているかの記録です。実装を読めば分かることは書かず、読んでも分からない「なぜ他の形にしなかったか」を残します。

## なぜ Stage Cam と別パッケージなのか

撮影と保持は、入力が Stage Cam のカメラであるかどうかに依存しません。Stage Cam の RenderTexture、タイムラプス専用に置いた Camera、利用者のカメラ props の出力など、RenderTexture か Camera であれば何でも入力にできます。Stage Cam へ組み込むと、Stage Cam を使わない利用者が撮影機能のためにカメラリグごと導入することになります。

依存の向きも同じ理由で決めています。このパッケージは Stage Cam を参照せず、Stage Cam もこのパッケージを参照しません。両者をつなぐのはシーン上の RenderTexture の参照だけです。

## 保存先を RenderTexture の配列にした理由

候補は 3 つありました。

| 方式 | 採らなかった理由 |
| --- | --- |
| 1 枚の大きな RenderTexture をタイルに分ける (atlas) | `VRCGraphics.Blit` は書き込み先の全体を書き換えるため、タイルへ書くには viewport を指定したカメラか、atlas 全体の複製が要ります。解像度と枚数の上限が 1 枚のテクスチャの最大サイズで決まり、特に Quest で小さくなります |
| `CustomRenderTexture` の update zone | 一部の領域だけを更新できますが、Udon から実行時に作れないため、大きさがアセットで固定になります。用途に応じて解像度と枚数を変えるという要件に合いません |
| RenderTexture の配列 | 採用 |

SDK 3.10.4 の Udon は `RenderTexture` のコンストラクタと `Create()` を公開しています。実行時に 1 枚ずつ作れるなら、配列にすれば書き込みは `Blit(src, frames[i])` だけで済み、上限は VRAM だけになります。間引きも配列の参照を並べ替えるだけで、GPU 上の複製が要りません。

保存枠は撮影で必要になった時点で作ります。最大枚数分を最初に確保すると、短時間しか撮らない場合にも最大の VRAM を占めるためです。

## 保存枠に深度を持たせない理由

公式文書によると、Quest の GPU では、shader に `ZTest Always` が無く、書き込み先が深度を持つ場合に `VRCGraphics.Blit` が失敗します。保存枠は Blit の書き込み先なので深度を持たせません。

Camera 入力では、通常のシーン描画に深度が要ります。保存枠ごとに深度を持たせる代わりに、深度付きの中間バッファを 1 枚だけ持ち、そこへ描いてから保存枠へ Blit します。24 bit の深度は 1 画素 4 byte なので、保存枠に持たせると VRAM が 2 倍になります。

## 撮影時刻を格子で決める理由

次の撮影時刻は「前回撮影した時刻 + 間隔」ではなく「前回の予定時刻 + 間隔」で決めます。前者はフレームごとの遅れがそのまま積み重なり、数時間の撮影では枚数が目に見えてずれます。後者は予定時刻が常に `開始時刻 + n × 間隔` に載るので、遅れは 1 フレーム分を超えて積み重なりません。

処理落ちや一時停止で複数回分の予定を過ぎた場合は、まとめて撮らずに次の格子へ戻ります。まとめて撮ると、同じ場面の画像が並ぶだけで保存枠を消費します。

撮影時計は `Time.timeAsDouble` の差分から求めます。`Time.deltaTime` を float で足し続ける方式は、90 fps で 3 時間の間に約 97 万回の丸めが入り、誤差が秒の単位に達しえます。

## 間引きの並べ替え

間引きでは、古い方から 0, 2, 4, ... 番目を残します。最古の 1 枚を必ず残すので、タイムラインの起点は何度間引いても撮影開始の時刻のままです。

捨てた枠の RenderTexture は破棄せず、配列の後ろへ回して次の撮影で再利用します。確保と破棄を繰り返さないためです。

枚数が偶数なら、間引き後の最後の画像の次の予定時刻は、間引き前の予定時刻と一致します。奇数の場合は一致しないため、間引いた回は撮影せず、次の予定を「最後に残した画像の時刻 + 新しい間隔」に決め直します。どちらの場合も、保持している画像は常に等間隔に並びます。

保持できる枚数が 1 枚の場合、間引くと撮影開始の画像が残らないため、停止として扱います。上書きにすると最初の画像が失われ、「撮影開始から現在までを覆う」という間引きの約束を守れません。この性質はオフライン層で検査しています (`repeated thinning keeps uniform spacing`)。

## 再生側が画像を複製しない理由

再生側は Recorder の RenderTexture をそのまま RawImage や MaterialPropertyBlock へ渡します。表示のために複製すると、同じ画像が VRAM に 2 枚載ります。

その代わり、Recorder の内容が変わると、同じ番号の画像が別の場面を指すことがあります (リングバッファの上書き、間引き)。再生側は Recorder の `revision` が変わるたびに、表示中の画像と同じ時刻に最も近い画像を二分探索で探して移ります。

## 計算部分の分離

Stage Cam と同じく、UdonSharp は `UdonSharpBehaviour` を継承したクラスしかコンパイルしないため、計算を static なヘルパークラスへ切り出せません。`CaptureRecorderSchedule.cs` と `CapturePlayerTimeline.cs` は、基底型も VRC の `using` も持たない部分クラスです。これらのファイルのメソッドは、フィールドを参照せず、必要な値をすべて引数で受け取ります。

この分離により、`.github/verify/offline/OfflineCaptureTests.cs` が Unity も VRChat も無い環境で計算部分を実行して検査します。

## 検証できないこと

- `VRCGraphics.Blit`、`Camera.Render()`、実行時の `RenderTexture` 生成が VRChat クライアント上で想定どおり動くこと。関数名が Udon に公開されていることは SDK の DLL で確認し、UdonSharp でコンパイルできることは `.github/verify/vrchat/` で確認しますが、実行結果は Build & Test でしか確かめられません。
- Quest 上での Blit の成否と VRAM の実使用量。
